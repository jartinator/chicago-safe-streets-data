# Agent-first layer for On Your Left! — static API under `site/api/v1/`

*Folded into the project 2026-07-13 from a standalone planning session
("scalable-quill"), reconciled against the current repo state and the
user-needs study (`docs/research/user-needs/REPORT-ux-proposal.md`). The
original plan predates the trust-hardening and one-pager merges (#19/#20)
and the gov-agent-layer work; where they conflicted, the current state
supersedes — every such edit is marked **[folded]**.*

## Context

The site today is built for human eyeballs: Leaflet maps, a ward table, findings prose. If LLM agents become the primary way people interact with this information ("how dangerous is my ward?", "is the Milwaukee route protected?", "what has my alderman done?"), the current surface fails them: there is no discovery entry point, no machine-readable schema, and the raw point layer (`crashes_cyclist.geojson`, 8.7 MB / 17,235 features) is too big to fetch into context. The foundations are unusually good, though — every record carries `data_tier`, `site/data/meta.json` is a ready-made provenance manifest, IDs are stable, and small rollups already exist.

**[folded] Fit with the user-needs study:** this plan is the machine-facing
half of the same program. The REPORT's "no API beyond flat-file downloads"
product gap gets closed by this layer; the P4 "provenance travels with the
artifact" principle maps 1:1 onto the `_meta` envelope; and the study's
kill-list rule that synthetic data must never pass as real becomes a hard
API requirement (below). The collaboration-principles "symmetric honesty"
rule applies: agents get the same tier/caveat discipline humans get.

**Decisions made with the user:**
- Audience: **public agents on the web** — any stranger's agent landing on the GitHub Pages site. Everything stays static; no server, no MCP, zero new runtime maintenance.
- Scope: **full agent-first layer** — discovery docs + JSON Schemas + reshaped agent-sized data files.
- Namespace: **new `site/api/v1/`** — a versioned "static API" folder, leaving the `site/data/` contract and front-end untouched. Pure additive.

Base URL: `https://jartinator.github.io/chicago-safe-streets-data/api/v1/`. Design goal: a cold agent goes from "never seen this site" to a cited answer in ≤3 fetches of <100 KB each.

## 1. File layout under `site/api/v1/`

All generated by the pipeline and committed (like `site/data/`), except `schemas/` which is hand-written:

```
site/api/v1/
  index.json                      # manifest/entry point: endpoints, example questions, fetch recipes (~8 KB)
  citywide.json                   # monthly trend + findings + mileage series + protected share (~35 KB)
  corridors.json                  # corridor table + hotspot intersections (~45 KB)
  wards/index.json                # 50-ward ranking (ward_safety_index minus the 107-month arrays) (~45 KB)
  wards/ward-01.json … ward-50.json   # ward deep dive: full index record, alderman, safety record,
                                      # menu spending, 311, top corridors, crashes_url (~15–35 KB)
  crashes/ward-01.json … ward-50.json # columnar crash slices: {columns, rows} (~30–150 KB; worst ward 42 = 1,092 rows)
  routes/index.json               # 21 main-route report cards, no geometry (~8 KB)
  routes/line-<line_id>.json      # per-line grade mix, pct_protected, member streets (~3–10 KB)
  council/index.json              # hearings + activity summary + pointers (~5 KB)
  council/records.json            # topic_relevant council matters (~90 KB)
  council/aldermen.json           # roster + safety-record aggregates + menu totals, keyed by ward (~70 KB)
  schemas/*.schema.json           # hand-written JSON Schema (draft 2020-12); envelope.schema.json $ref'd by all
```

Conventions: kebab-case, zero-padded `ward-NN`, compact single-line JSON via existing `socrata.write_json`. GitHub Pages serves JSON with `access-control-allow-origin: *`, so browser agents can fetch too.

**Shared `_meta` envelope on every file:** `api_version`, `contract_version`, `generated_at` + `provenance` (copied from `site/data/meta.json`), `data_tier` (+ `tier_note` for mixed-tier files; per-section `data_tier` stays inside payloads per existing convention), `license`/`attribution` strings, `schema` URL, `human_page` URL, `docs` → llms.txt.

**Crash slices** are columnar (`{"columns": [...], "rows": [[...]]}`) with: `crash_id` shortened to a 16-hex prefix (emit asserts prefix uniqueness, falls back to full id on collision; documented in schema), coords rounded to 5 decimals, low-value fields dropped (full detail remains in `site/data/crashes_cyclist.geojson`).

**[folded] Synthetic data is excluded from the API namespace entirely.**
`obstructions_mock.geojson` gets no `api/v1/` endpoint, no llms.txt mention
beyond an explicit "there is NO obstruction data; the mock schema preview is
synthetic and must never be cited" line, and the index manifest carries the
same statement. Rationale: DECISIONS.md #22 (badges don't survive
screenshots; for agents, tier fields don't survive summarization). An agent
answering "how often is the Milwaukee lane blocked?" must find an honest
"no data yet", never a synthetic number.

**[folded] Naming:** anywhere the API describes `comparable_danger_score`,
the description string is "relative concern rank among wards, higher =
worse — not absolute risk" (the field name itself is contract and stays).
Ward files include `one_pager_url` (→ `ward.html?ward=N`) and every file's
`_meta.methodology` links `methodology.html` — the recitable-methodology
requirement (REPORT P5) applies to machine consumers too.

## 2. Pipeline: new `pipeline/emit_api.py`

Same style as `aggregate.py`/`refresh_reporting.py`: pure unit-testable builders + `emit_all()`.

- Reads only committed `site/data/*` (no network, no `raw/`) — so the real API can be populated immediately with `python pipeline/emit_api.py`, no live Socrata pull needed.
- Builders: `build_index`, `build_citywide`, `build_corridors_api`, `build_wards_index`, `build_ward_file`, `build_crash_slice`, `build_routes_index`, `build_line_file`, `build_council_index`, `build_council_records_api`, `build_aldermen_api`, plus `build_llms_txt` and `build_sitemap` (generated so record counts/dates never go stale).
- `emit_all()` writes everything, prints a size table (mirrors run_all's timing-table ethos), **fails hard if any file exceeds budget**, and prunes stale generated `ward-*`/`line-*` files (never touches `schemas/`).
- Council data preserves DECISIONS.md #8: no fuzzy alderman matching; unmatched sponsors go in an `unmatched_sponsors` list.

**Config additions** (`pipeline/config.py`): `API_VERSION = "1"`, `SITE_API_DIR`, `SITE_BASE_URL`, `API_SIZE_BUDGET_BYTES = 100_000`, `API_CRASH_SLICE_BUDGET_BYTES = 150_000`, `CRASH_ID_PREFIX_LEN = 16`; bump `CONTRACT_VERSION` "1.9" → "1.10" (additive, logged in SCHEMA.md).

**Wiring:**
- `pipeline/run_all.py`: append `["emit_api.py"]` to `COMMON_STAGES` after `aggregate.py` (covers live and `--fixtures`); update docstring stage list.
- `pipeline/refresh_reporting.py`: call `emit_api.emit_all()` at end of `main()`.
- `pipeline/check_provenance.py`: also load `site/api/v1/index.json` (if present) and fail unless `_meta.provenance == "socrata"` and `generated_at`/`contract_version` match `site/data/meta.json` (catches stale or fixtures-built API).
- `.github/workflows/data-guard.yml`: add `site/api/**` to both `paths` lists.

## 3. JSON Schema strategy

- Hand-written schemas in `site/api/v1/schemas/` are **the normative contract for the API namespace** (published — every `_meta.schema` URL resolves). `SCHEMA.md` stays normative for `site/data/` and gains a short "Contract v1.10 (agent API)" section deferring field detail to the schemas.
- No prose↔schema generation; drift is caught by CI:
  - `jsonschema>=4.21` added to `pipeline/requirements-dev.txt`.
  - New `pipeline/check_api.py` (sibling of check_provenance): validates every committed API file against its declared schema (local ref registry, no network), checks size budgets, provenance/version coherence, and manifest completeness (every `index.json` endpoint exists on disk and vice versa). Runs in data-guard CI + locally in the weekly-refresh review.

## 4. Discovery artifacts

- **`site/llms.txt`** (generated): title + one-paragraph description, "start here" → `api/v1/index.json`, endpoint list with example questions, a "reading the data" section (tier vocabulary, provisional-data caveat, `_meta` envelope, **[folded]** the no-synthetic-data statement and the "raw counts, not ridership-normalized" caveat verbatim), links to human pages **[folded] including methodology.html and the ward one-pagers**.
- **`site/robots.txt`** (static): allow all + `Sitemap:` line.
- **`site/sitemap.xml`** (generated): **[folded]** all current HTML pages — index, network, findings, table, sources, methodology, action, ward (base URL only; per-ward views are query-param), contributing — plus llms.txt and the API index; `lastmod` from `meta.json.generated_at`. `obstructions-preview.html` is deliberately omitted (gated demo page, not for indexing).
- **HTML head**: `<link rel="alternate">` to `api/v1/index.json` and `llms.txt` on all pages; schema.org `Dataset` JSON-LD block in `index.html`.
- **Docs**: README "For agents (static API)" section; CONTRIBUTING one-liner routing API contract changes to `schemas/`; **[folded] DECISIONS.md #23** (the plan predated #21 coverage-denominator and #22 mock-watermark) — "Agent-first consumption is a static, versioned mirror, not a service" (records the no-server rationale, the additive namespace, hand-written-schemas choice, crash-id-prefix trade-off, and the synthetic-data exclusion).

## 5. Testing & verification

New offline tests in `pipeline/tests/` (existing style, synthetic inputs):
- `test_emit_api.py` — envelope propagation (incl. fixtures provenance), ward/alderman merge, crash-slice columns + prefix-collision fallback, pruning, wards index = 50 entries with no `monthly`; **[folded]** an explicit test that no `api/v1/` file references obstruction data.
- `test_api_schemas.py` — every builder output validates against its schema (Draft 2020-12, local `referencing` registry).
- `test_api_sizes.py` — synthetic worst case (1,200-crash ward) stays under budget.
- Update `test_run_all_order.py`; add coverage for the check_provenance extension.

CI: extend data-guard with `pip install jsonschema` + `python pipeline/check_api.py` (stays geopandas-free). Optional separate PR: `.github/workflows/tests.yml` running pytest on `pipeline/**` PRs (repo currently has **no** test CI — at minimum scope it to the new API tests, which don't need geopandas).

End-to-end verification:
1. `python pipeline/run_all.py --fixtures` → `site/api/v1/` populated with `provenance: "fixtures"`; `check_provenance.py` correctly fails.
2. Restore real `site/data`, run `python pipeline/emit_api.py` alone → real API; `check_provenance.py` + `check_api.py` pass; review size table.
3. `python pipeline/refresh_reporting.py` regenerates the API coherently.
4. Post-deploy: curl Pages URLs for `llms.txt`, `api/v1/index.json`, one ward file, one schema; walk a cold-agent flow (index → recipe → 2 fetches answers "how dangerous is ward 40?").

## 6. Phasing (incremental PRs, each pure-additive; deploy.yml needs no change)

1. **Skeleton + wiring** — config, `emit_api.py` with index/citywide/corridors + envelope, run_all/refresh_reporting wiring, check_provenance extension, core tests, data-guard paths. Commit generated files.
2. **Ward layer** — `wards/*`, `crashes/*`, size tests, pruning.
3. **Routes + council** — `routes/*`, `council/*`.
4. **Schemas + CI validation** — `schemas/`, jsonschema dep, schema tests, `check_api.py`, data-guard step, optional tests.yml.
5. **Discovery + docs** — llms.txt/sitemap/robots, HTML head links + JSON-LD, README/CONTRIBUTING/SCHEMA.md v1.10, DECISIONS.md #23, CONTRACT_VERSION bump.

**[folded] Sequencing vs. the UX roadmap:** this layer slots after the
Tranche-1 items already shipped (#19/#20) and runs parallel to Tranche 2 —
it touches `pipeline/` + new namespaces only, so it never conflicts with the
resident-register / equity-context UI work. Best ordered after the live data
refresh so the first published API carries `provenance: "socrata"`.

## Risks / trade-offs (accepted)

- Crash-id prefixing is the only lossy trim — mitigated by uniqueness assertion + schema documentation.
- Generated llms.txt/sitemap churn on each weekly refresh — acceptable; keeps counts honest.
- Hand-written schemas can drift from builders — exactly what `check_api.py` + schema tests catch on every PR touching `pipeline/**` or `site/api/**`.
- **[folded]** Agents may still summarize away caveats no matter how loud the
  envelope is — the mitigations (synthetic exclusion, caveat strings inside
  the payloads themselves, description-field framing) reduce but cannot
  eliminate this; same accepted residual as human screenshots.
